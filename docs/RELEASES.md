# Выпуски pet-companion и обновление проектов

Как выходит версия и как проект, который использует библиотеку, проверяет её и переходит на неё. Порядок команд выпуска для сопровождающего — `CONTRIBUTING.md`, «Выпуск»; здесь — устройство цепочки, гарантии и подключение своего проекта. Документ не входит в пакет npm.

## Гарантии

- **Опубликованное не меняется.** Версию не публикуют повторно, тег `vX.Y.Z` не переносят, файл выпуска GitHub не заменяют. Исправление — новая версия; неудачную версию можно пометить `npm deprecate`. Теги `v0.2.0` и `v0.2.2` так и остались тегами без публикации: CI их коммитов был красным.
- **В npm и на GitHub — один и тот же файл**, упакованный из коммита тега, а не из рабочей папки. Его SHA-256 и npm integrity названы в описании выпуска GitHub, GitHub показывает digest файла, реестр — `dist.integrity`. Три источника независимы: подмену в одном видно по двум другим.
- **Публикация — только после зелёного CI того же коммита на теге**, и CI упаковал то же содержимое, что публикуется.
- **Выпуск ничего не обновляет сам.** Проект переходит на новую версию своим решением и своими проверками; установленное мобильное приложение получает новую версию только новой сборкой и доставкой. Данные пользователей выпуск не трогает и не синхронизирует.

## Отпечатки архива

`node scripts/release.mjs record` упаковывает коммит: `git archive` → временная папка → `npm pack --ignore-scripts`. Запись `record.json`:

| Поле | Что это |
| --- | --- |
| `sha256`, `integrity`, `sha1` | байты `.tgz` — то, что публикуется и что проверяет npm |
| `tarSha256` | несжатый tar |
| `filesSha256` | пути и SHA-256 каждого файла пакета |
| `commit`, `version`, `files`, `size`, `node`, `npm` | откуда и чем упакован |

Gzip одного и того же tar зависит от zlib версии Node: 2026-10-20 коммит `c1140af` (0.2.3) на Node 25.8.2 с npm 11.11.1 и с npm 10.9.4 дал ровно опубликованный `.tgz` (SHA-256 `75d01a29…3416`), а на Node 24.22.0 — другой `.tgz` с тем же tar (`tarSha256` `34aaa856…93bf`). Поэтому CI (Node 22) и повторная упаковка сверяются **по содержимому** (`filesSha256`, `tarSha256`), а публикуется и сверяется **побайтно** сам записанный `.tgz`.

## Цепочка и отказы

| Шаг | Команда | Что проверяется | При отказе |
| --- | --- | --- | --- |
| Кандидат | `node scripts/release.mjs prepare X.Y.Z --candidate --out DIR` | чистое дерево; номер одинаков в `package.json`, `manifest.json`, `VERSION`, есть раздел CHANGELOG `## X.Y.Z`; тега ещё нет; номера нет в npm; архив из `HEAD`, запись; `npm test`, `test:browser`, затем `test:package` и `test:consumers` **на этом архиве** (`PET_TARBALL`) | записи нет или в ней непрошедшая проверка — публиковать нечего |
| Тег и CI | `git tag -a vX.Y.Z`, `git push origin main vX.Y.Z` | CI тега: те же четыре набора и шаг «Запись архива» (`record --expect-tag vX.Y.Z` — номер в коммите согласован с тегом), артефакт `release-record` | красный CI — публикации нет; тег не переносят, исправление — новый номер |
| Публикация | `node scripts/release.mjs publish DIR/record.json` | архив = запись (SHA-256, integrity, содержимое), нет непрошедших проверок; аннотированный тег локально и на `origin` — тот же объект и коммит записи; последний запуск CI на push тега — `success`; запись CI — то же содержимое; номера нет в npm (тот же архив — шаг пропускается, другой — отказ); выпуска GitHub нет (с тем же файлом — пропуск, с другим — отказ) | ничего не опубликовано; повтор после частичного сбоя доводит до конца без второй публикации |
| Сверка | `node scripts/release.mjs verify X.Y.Z [--record DIR/record.json]` | архив из npm = `dist.integrity`; в нём `package.json` этой версии, записи только внутри `package/`; файл выпуска GitHub — те же байты и digest; описание называет его SHA-256 и integrity; тег GitHub → коммит (записи); повторная упаковка коммита тега — то же содержимое | код 1 и список расхождений |

`npm publish` архива (`.tgz`) не запускает скрипты пакета — в том числе `prepublishOnly` (проверено `test/release.test.mjs`); защита выпуска — гейты `publish`, а не `prepublishOnly`. Под терминалом `publish` передаёт npm ввод-вывод: веб-подтверждение двухфакторной проверки npm 11 работает только с TTY.

Проверки цепочки: `test/release.test.mjs` (часть `npm test`, без сети) — игрушечный пакет в своём git с тегом и `origin`, локальный реестр и API GitHub (`test/registry-stub.mjs`), поддельный `gh` (`test/fakes/gh.mjs`): упаковка из коммита, независимость от gzip, каждый отказ публикации до реестра и GitHub, успешная публикация ровно записанного архива, повтор без изменений, расхождения `verify`.

## Состояние на 2026-10-20 (PL12)

- **Реализовано и проверено локально:** `scripts/release.mjs`, `test/release.test.mjs`, `PET_TARBALL` у `test:package` и `test:consumers`, шаг «Запись архива» в `.github/workflows/ci.yml`. `verify` 0.2.1 и 0.2.3 по настоящим npm и GitHub — все пункты сходятся, повторная упаковка коммитов тегов дала ровно опубликованные байты. `verify 0.2.2` — расхождения (в npm и выпусках GitHub её нет). Публикация записи тега `v0.2.2` остановлена гейтом CI (последний запуск тега — failure) до обращения к реестру. Полный путь `publish` записи тега `v0.2.3` — в локальный реестр с настоящими тегом, CI и выпуском GitHub: без записи CI — отказ; с `--ci-record skip` (CI 0.2.3 был до PL12) — в реестр ушли ровно байты записи, повтор ничего не публикует, подмена после публикации видна `verify`.
- **Не включено:** шаг записи архива в CI начнёт работать после push этих изменений в `main` библиотеки — до этого ни один запуск CI артефакта `release-record` не имеет, и `publish` без `--ci-record skip` откажет. Публикация остаётся ручной с Mac владельца (вход npm и подтверждение 2FA — действие владельца). Публикация из CI (доверенная публикация npm через OIDC) не настроена: для неё владельцу нужно указать репозиторий и workflow в настройках пакета на npmjs.com и разрешить `id-token: write` — отдельное решение.

## Подключение своего проекта

1. **Точная версия.** `npm install --save-exact pet-companion@X.Y.Z` (в `package.json` — `"pet-companion": "X.Y.Z"`, без `^` и `~`), `package-lock.json` — в git; установка на сервере и в CI — `npm ci` (npm сверяет integrity из lock). До 1.0 `^0.2.x` не принимает 0.3; patch-версии совместимы по CHANGELOG, но переход всё равно проверяется своими тестами.
2. **Проверка выпуска перед переходом** — три независимых источника должны назвать один файл:

   ```sh
   V=0.2.3
   npm view pet-companion@$V dist.integrity          # реестр
   npm pack pet-companion@$V --json | grep -E '"(integrity|shasum)"'   # скачать архив; полный integrity
   shasum -a 256 pet-companion-$V.tgz                 # SHA-256 архива
   gh release view v$V --repo jivchic88/pet-companion # описание: «SHA-256» и «npm integrity», файл выпуска
   ```

   Без `gh` — `https://github.com/jivchic88/pet-companion/releases/tag/v$V` (там же digest файла). Полная сверка с повторной упаковкой коммита тега — из клона репозитория: `node scripts/release.mjs verify $V`. Расхождение — не переходить и сообщить в issues репозитория.
3. **Переход — предложением, а не автоматическим слиянием.** Ветка или PR, где изменены только версия в `package.json` и запись `pet-companion` в lock; CI проекта запускает свои проверки: подключение (`mountPet` или `mountPetIn` поднимаются, файлы по `manifest.json` отдаются без 404, если сайт без сборщика), свои сценарии и сохранность данных пользователей. Сливать после зелёных проверок и чтения CHANGELOG между версиями. Автоматизации PR — на выбор проекта; примеры (в этой серии не запускались):
   - Dependabot (`.github/dependabot.yml`): `package-ecosystem: npm`, `allow: [{ dependency-name: pet-companion }]`, `versioning-strategy: increase` — точная версия остаётся точной;
   - Renovate: `packageRules` с `matchPackageNames: ["pet-companion"]`, `rangeStrategy: "pin"`, `automerge: false`.

   Образец полной проверки перехода — `scripts/pet-update.mjs` тренажёра (репозиторий тренажёра закрыт; порядок описан в его ADR 0024): доверие трём источникам, совместимость до установки, установка в отдельном клоне только пакета питомца, проверки потребителя, PR без слияния и деплоя.
4. **Откат** — `git revert` коммита перехода и `npm ci` (вернутся прежние `package.json`, lock и ровно прежний архив) либо переход на прежнюю точную версию тем же порядком. Данные: новые версии читают записи прежних; прежняя версия после отката сохраняет поля, которых не знает, в пределах README, «Хранение», — но вкладка, открытая до обновления, пишет по правилам своей версии до перезагрузки.
5. **Мобильное приложение** получает новую версию только своей сборкой и доставкой (магазины, OTA — правила проекта); выпуск библиотеки установленные приложения не обновляет. Натив предварительный — README, «Поддержка платформ».
