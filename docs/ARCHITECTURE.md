# Архитектура pet-companion: общее ядро, команды и расширения

**Статус документа:** проект архитектуры (этап PL01), 2026-10-12. Описывает выпущенную версию **0.1.4** и выбранный **целевой контракт**, который ещё **не реализован**. После `npm install pet-companion@0.1.4` доступно только то, что описано в README («Интерфейс»): `mountPet`, `localDay`, `VERSION`, методы экземпляра `update`, `notify`, `open`, `close`, `destroy`, свойства `version`, `mounted`, `opened`. Всё остальное в этом документе — проект: методы `setName`, `feed`, `getState`, `subscribe` и другие, входы `pet-companion/core`, `/web`, `/native` и т. п. сейчас не существуют.

Документ не входит в пакет npm и не меняет поведение, интерфейс, ключи и форматы хранения, версию.

## 2. Цели и границы

**Цели [цель]:** одна реализация поведения для веба и нативных приложений; простые команды `pet.*` вместо нажатий на встроенные кнопки; питомцы и модели поведения подключаются определениями; хранение честно различает «сохранено», «сохраняется» и «не сохранилось»; существующие подключения 0.1.4 продолжают работать.

**Не входит:** сеть, синхронизация устройств, сервер, аналитика; оценка ответов, личности, рейтинги; штрафы за отсутствие; удалённая загрузка исполняемого кода; универсальный SDK для любых платформ; общий отображающий слой для веба и натива (одинаковый вид не обещается — общий смысл и правила).

**Принципы:** ядро — единственная реализация правил; отображение рисует и распознаёт ввод, но не решает; хост сообщает о подтверждённых действиях и даёт счёт; хранение — через порт с честным результатом; время и случайность — через порты; каждый экземпляр владеет своим состоянием.

### 3.1 Граф импортов [цель]

- `pet/core/**` импортирует только `pet/core/**`. Ни одного импорта `pet/defs`, `pet/web`, `pet/native`, `pet/storage`, рисунков, CSS и внешних пакетов.
- `pet/defs/**` импортирует только `pet/core/define.mjs` (проверка определений) и `pet/defs/**`.
- `pet/web/**` (legacy и контейнер, веб-наборы, веб-адаптеры хранения) — `pet/core/**`, `pet/defs/**`, `pet/web/**`.
- `pet/react/**` — `pet/web/**`, `pet/core/**` и `react` (необязательная зависимость-партнёр).
- `pet/native/**` — `pet/core/**`, `pet/defs/**`, `pet/native/**`, `react`, `react-native`, `react-native-svg` (необязательные партнёры).
- `pet/storage/sqlite.mjs` — `pet/core/**` и `expo-sqlite` (необязательный партнёр).
- `pet/pet.mjs` (вход `pet-companion`) — фасад legacy поверх `pet/web/legacy/**`.
- Ядро и определения не содержат обращений к `window`, `document`, `navigator`, `localStorage`, `indexedDB`, `matchMedia`, `crypto`, `fetch` ни при загрузке, ни при исполнении. Проверка (PL03 и далее): импорт и сценарии ядра в Node с этими глобалами-ловушками; разбор графа импортов из архива пакета (`test:package`).
- В `pet/core/**` нет идентификаторов конкретных питомцев (`'cat'`, `'dog'`), кроме модуля совместимости форматов 0.1.4 `pet/core/formats/legacy.mjs` (ключи `cat`, `companion.dog` по своей природе привязаны к коту и собаке). Проверка — PL06.

## 4. Экземпляр ядра

### 4.1 Создание, запуск, отключение [цель, PL03; публично — PL05]

```text
createPetCore(options) ──► status 'created' ──start()──► 'running' ──destroy()──► 'destroyed'
                     (без побочных действий)                     (повторный destroy — ничего)
```

`createPetCore(options) → PetCore` — синхронно. Создание читает подтверждённое из уже загруженного хранилища, проверяет определения и не пишет, не планирует таймеров и не вызывает подписчиков.

| Настройка | Что | Обязательна |
| --- | --- | --- |
| `storage` | адаптер хранения (§ 8), загруженный: `storage.status` — `'ready'` или `'failed'` | да |
| `scenes` | резервирование сценки (§ 9); `null` — сценок нет | нет (по умолчанию `null`) |
| `pets` | массив `PetDefinition` (≥ 1), ID уникальны | да |
| `behaviors` | массив `BehaviorDefinition` (≥ 1), ID уникальны | да |
| `progress` | `() => { marks, today, limit }` — как в 0.1.4: быстро, без побочных действий, вызывается часто | нет (`{ marks: 0, today: 0 }`) |
| `clock`, `random`, `scheduler`, `log` | порты (§ 4.3); по умолчанию — системные | нет |

Ошибки создания — исключение `PetError` с `code`: `invalid-options`, `storage-not-loaded`, `definition-invalid`, `duplicate-id`, `unsupported-format`, `incompatible-definitions`. Это ошибки интегратора, они обнаруживаются сразу. Фасады, которые по контракту не бросают (legacy `mountPet`, § 6.2), перехватывают их и возвращают неподключённый экземпляр.

`start()` — один раз: применяет первое включение (без исторических наград), приветствие дня, планирует покой и полночь (`scheduler`), начинает принимать входы. До `start()` команды допустимы и меняют состояние, но реакции и таймеры не запускаются; так отображение успевает подписаться и получить первый снимок до первых эффектов. Повторный `start()` — результат `{ ok: false, error: { code: 'already-started' } }`.

`destroy()` — синхронно и идемпотентно: статус `'destroyed'`; отменяются все задачи `scheduler`; подписчики получают последнее обновление `{ reason: 'destroyed' }` и снимаются; экземпляр снимается с рассылки изменений хранилища; поздние результаты хранения и резервирования ничего не меняют (§ 4.5); уже принятые адаптером операции записи выполняются им (§ 8.8). Ресурсы отображения (элементы, слушатели, захваты указателя, кадры) снимает отображение, получив `'destroyed'`, — и при `destroy()`, вызванном хостом у ядра, и при `destroy()` фасада.

### 4.2 Владение ресурсами

| Ресурс | Владелец | Снимается |
| --- | --- | --- |
| состояние экземпляра (настройки в памяти, режиссёр, память событий, попытка сценки, открытый вид, черновик комнаты, позиции игрушек) | экземпляр ядра | `destroy` (теряется; несохранённые правки не становятся сохранёнными) |

### 4.3 Порты

```ts
// Проект интерфейсов (PL03), не API 0.1.4.
interface Clock {
  now(): number;                 // мс эпохи — только для интервалов (длительности, паузы, сроки)
  day(at: number): string;       // местная дата 'ГГГГ-ММ-ДД' момента at — граница лакомства, приветствия, сценок
  nextDay(at: number): number;   // момент начала следующего местного дня (не раньше at + 1000)
}
type Random = () => number;      // [0, 1)
interface Scheduler {
  later(ms: number, task: () => void): () => void; // однократно; возвращает отмену
}
interface Log { warn(message: string, error?: unknown): void }
```

По умолчанию: `Date` (`localDay` — системная реализация `day`), `Math.random`, `setTimeout`/`clearTimeout`, `console.warn('Питомец:', …)`. Ни один порт не используется при загрузке модуля — только после `createPetCore`. Хранилище и резервирование — § 8, § 9.

### 4.4 Время и случайность

- **Интервалы и календарь раздельно.** Длительности реакций, паузы повторов, срок сценки (10 с), задержка старта (500 мс), покой (3 мин), отложенная реакция (60 с) считаются по `clock.now()`. Лакомство, приветствие и день сценки — по `clock.day(now)`. Полночь — задача на `clock.nextDay(now) − now`; кроме того, день пересчитывается при каждой команде, зависящей от дня (`feed`, `notify`, `refresh`), и при возврате видимости — перевод часов, смена пояса и усыплённое устройство не оставляют «вчерашний» день.
- **Воспроизводимость.** При одинаковых определениях, начальном хранилище, последовательности входов, значениях `clock` и `random` и порядке срабатывания задач `scheduler` ядро даёт одинаковую последовательность снимков и эффектов на любом адаптере. Тесты используют ручной планировщик (продвижение времени вручную) и заданную последовательность случайных чисел. Метка вкладки для дня сценки (`by`) строится из `random` и `now`, а не из `crypto`.
- **Где используется случайность:** выбор реплики, шанс и вариант сценки, интервалы моргания и одиночных движений, зевок, выбор движения при открытии уголка.

### 4.5 Отмена задач и устаревшие результаты

- Каждая задача ядра планируется через обёртку с **поколением экземпляра** и **именем задачи**: повторное планирование задачи с тем же именем отменяет прежнюю (как `later(key)` 0.1.4); `destroy` отменяет все и увеличивает поколение. Сработавшая задача сверяет поколение и ничего не делает, если экземпляр отключён, — даже если планировщик не смог её отменить.
- Асинхронные результаты (запись, резервирование сценки, `done` команды) сверяют живость экземпляра, а резервирование — ещё и **попытку** (её объект, § 9). Поздний результат прежнего экземпляра не меняет ни его, ни новый экземпляр, ни копию дня сценки.
- Ядро не держит ссылок на отображение; отображение подписано на ядро и снимает себя по `'destroyed'`.

### 5.2 Снимок [цель, PL05; срез — PL03]

`getState(): PetSnapshot` — глубоко замороженный объект из простых данных (строки, числа, булевы, массивы, объекты; без функций, DOM и данных хоста). Один и тот же объект возвращается, пока состояние не изменилось (стабильная ссылка — нужна `useSyncExternalStore`); любое изменение даёт новый объект. Изменить через снимок внутреннее состояние нельзя.

```ts
// Проект (PL05). Поля добавляются только совместимо; v — версия формата снимка.
interface PetSnapshot {
  v: 1;
  status: 'created' | 'running' | 'destroyed';
  storage: 'ready' | 'failed';                    // загрузка хранилища
  pet: { id: string; shown: string; available: boolean };      // shown ≠ id — показ запасного (§ 7.5)
  behavior: { id: string; shown: string; available: boolean };
  name: { value: string; chosen: boolean; display: string };    // chosen=false — имя ещё не выбирали
  look: { coat: string; accessory: string; worn: string };      // worn — надетый с учётом ступени
  prefs: { motion: 'normal' | 'calm' | 'none'; phrases: boolean; reducedMotion: boolean; effectiveMotion: 'normal' | 'calm' | 'none' };
  presence: { mode: 'always' | 'on-call'; hidden: boolean; surface: 'pet' | 'call' | 'none'; around: boolean };
  visible: boolean;
  progress: { marks: number; today: number; limit: number | null; stage: number; next: { at: number; title: string } | null; toNext: number; seenStage: number; fresh: string[] };
  treat: 'waiting' | 'ready' | 'fed';
  pose: { base: 'calm' | 'attentive' | 'rest' | 'content'; resting: boolean;
          reaction: null | { type: string; pose: string; until: number; toward: string; mini: string; tryOn: string; explicit: boolean; scene: boolean } };
  phrase: null | { text: string; short: string; until: number };  // облако реплики
  scenePhrase: string;                                            // реплика под сценой открытого уголка
  context: { focus: boolean; quiet: string[] };
  view: { open: null | 'corner' | 'play' | 'room'; source: '' | 'pet' | 'call' };
  play: null | { toys: Record<string, { at: [number, number] | null }>; outcome: string };
  room: { pos: Record<string, [number, number]>; feedShift: [number, number];
          draft: null | { pos: Record<string, [number, number]>; pick: string; changed: string[]; other: boolean; failed: boolean; saving: boolean } };

```

Хост не получает в снимке учебного шага, навигации и оценок — их нет в ядре.

### 5.3 Эффекты

Одноразовые события отдельно от снимка: их нельзя восстановить чтением состояния, и повтор снимка не повторяет их.

| Эффект | Когда | Отображение |
| --- | --- | --- |
| `{ type: 'announce', text }` | сообщение для скринридера (тексты 0.1.4: «… получает лакомство. Сегодня уже угостили», «Расстановка сохранена.», «Имя: …») | веб — `aria-live` с задержкой 80 мс, как 0.1.4; натив — `AccessibilityInfo.announceForAccessibility` |
| `{ type: 'celebrate', stage, items, accessories }` | открыта новая ступень | подсветка новой вещи |
| `{ type: 'micro', kind, ms }` | одиночное движение покоя (моргание, ухо, хвост, взгляд, наклон) | короткая анимация |
| `{ type: 'arrive' }` | питомец устроился на новом месте или виде по действию владельца | анимация появления |
| `{ type: 'save', key, op, result }` | операция записи завершилась (`'saved'` или `'failed'`) — и синхронная, и поздняя | по желанию: «Сохраняется…» → итог |
| `{ type: 'warning', code, message }` | диагностический сбой внутри ядра, который не помешал команде | журнал |

### 5.4 Подписка

`subscribe(listener, { initial = true } = {}) → unsubscribe`; `listener(update)`, где `update = { snapshot, effects, reason }`.

- **Начальная доставка:** при `initial: true` слушатель вызывается один раз синхронно, до возврата из `subscribe`, с текущим снимком, `effects: []`, `reason: 'initial'`.
- **Порядок:** каждое изменение — одно обновление (снимок сразу после изменения и его эффекты в порядке возникновения). Обновления доставляются по очереди (FIFO): одно — всем подписчикам в порядке подписки, затем следующее.
- **Повторный вход:** команда, вызванная из слушателя, выполняется сразу и синхронно возвращает результат; её обновление встаёт в очередь доставки после текущего. Поэтому `getState()` внутри слушателя может быть новее переданного ему снимка; переданный снимок — состояние сразу после своего изменения.
- **Отписка** действует немедленно: отписанный не получает и оставшиеся в текущем раунде обновления. Подписка во время доставки получает начальный снимок и только обновления, возникшие после неё.
- **Исключение слушателя** перехватывается: `log.warn`, доставка остальным продолжается, команда не откатывается, слушатель остаётся подписан.
- **`destroy`:** последнее обновление `reason: 'destroyed'` со статусом `'destroyed'`, затем все отписаны. `subscribe` после `destroy` при `initial: true` один раз сообщает снимок `'destroyed'` и возвращает пустую отписку.

### 5.5 Порядок обработки команды

1. Экземпляр отключён → `{ ok: false, error: { code: 'destroyed' } }`, без изменений и эффектов.
2. Проверка аргументов → `invalid-argument`, `unknown-id`, `unsupported` — без изменений.
3. Бизнес-правило (лакомство сегодня ещё недоступно, питомец спрятан, вид не открыт, аксессуар не открыт) → отказ с кодом — без изменений.
4. Изменение состояния в памяти — сразу и синхронно.
5. Постановка операций записи (`storage.write(key, build)`); синхронный результат обрабатывается здесь же (§ 8.5).
6. Оркестровка: запрос реакции режиссёру, планирование и отмена задач.
7. Эффекты (тексты объявлений учитывают уже известный результат записи).
8. Одно обновление подписчикам — синхронно, до возврата из команды; если команда вызвана из слушателя, её обновление доставляется после текущего (§ 5.4), но тоже до возврата управления хосту из внешней команды.
9. Результат команды.

Поздний асинхронный результат записи — отдельное изменение: шаги 4 (статус), 7 (эффект `save` и, где 0.1.4 сообщает о сохранении, объявление), 8.

### 6.2 Совместимость legacy [0.1.4 → цель]

Сохраняется без изменения поведения корректных подключений:

- `mountPet(options)` синхронен, не бросает исключений, при отказе — `console.error('Питомец не подключён: …')` и экземпляр с `mounted === false`; отказ не оставляет элементов, слушателей, отметок на `<html>` и не трогает сохранённое; проверка настроек — до любых действий (список причин — README, «Отказ подключения»).
- Один питомец на странице и реестр `globalThis[Symbol.for('pet-module')]`; новое подключение отключает прежнее; совместимость с копией 0.1.1 и копиями 0.1.2+.
- `pet.update()`, `pet.update(flags)`, `pet.notify('saved', detail | null)`, `pet.notify('failed')`, `pet.open('corner' | 'play')`, `pet.close({ restore })`, `pet.destroy()` возвращают `undefined`, как в 0.1.4; методы отключённого экземпляра ничего не делают; повторный `destroy()` безопасен.
- `pet.version`, `pet.mounted`, `pet.opened` — прежний смысл.
- Настройки `storage`, `places`, `progress`, `step`, `go`, `zone`, `home`, `classes`, `texts`, ключи и форматы `v1`, классы и переменные CSS, отметки на `<html>`, id `cat-*` — прежние.
- Событие без `key` — как в 0.1.4 (Р2): фасад передаёт ядру `String(detail.key)`.

С PL03 фасад создаёт экземпляр ядра (`createPetCore` + веб-адаптер хранения, загруженный синхронно) и legacy-отображение; синхронный порядок 0.1.4 сохраняется (§ 8.5). С PL05 объект `pet` получает дополнительно методы ядра из § 6.4 (кроме совпадающих по имени `update`, `notify`, `open`, `close`, `destroy`, которые сохраняют legacy-сигнатуру) и свойство `pet.core` — экземпляр ядра (`null`, пока не подключён). `pet.core.notify(...)` возвращает результат ядра; `pet.destroy()` и `pet.core.destroy()` отключают всё.

### 6.3 Результат команды и ошибки

```ts
// Проект (PL05).
type CommandResult<Extra = {}> =
  | ({ ok: true; changed: boolean; save: SaveReport } & Extra)
  | { ok: false; error: { code: ErrorCode; message: string } };

interface SaveReport {
  status: 'none' | 'saved' | 'pending' | 'failed'; // none — писать нечего
  keys: string[];                                  // затронутые ключи хранения
  done?: Promise<'saved' | 'failed'>;              // только при 'pending'; никогда не отклоняется
}
```

- **Бизнес-отказ** (`ok: false`) — ничего не изменилось. **Изменение в памяти** (`ok: true`) — правка действует сразу, даже если не сохранилась. **Подтверждённое сохранение** — только `save.status === 'saved'` либо `done`, разрешившийся в `'saved'`. `'pending'` — операция принята в очередь, это не «сохранено».
- `done` сообщает действительный итог операции адаптера, даже если экземпляр уже отключён (операция выполняется очередью, § 8.8); отключённый экземпляр при этом не меняется и эффектов не шлёт.
- Команды ядра не бросают исключений. Внутренний сбой — `{ ok: false, error: { code: 'internal' } }` и `log.warn`; состояние до сбоя сохраняется, насколько это достижимо.
- Методы экземпляра не зависят от `this`: их можно передавать отдельно (`useSyncExternalStore(core.subscribe, core.getState)`).

| Код | Значение |
| --- | --- |
| `invalid-argument` | тип или значение аргумента вне допустимого |
| `unknown-id` | ID питомца, модели, облика, аксессуара или предмета не зарегистрирован |
| `unsupported` | возможность не поддерживается питомцем или текущим отображением (нет лапы, нет редактора комнаты) |
| `locked` | аксессуар ещё не открыт ступенью |
| `hidden` | питомец спрятан |
| `away` | присутствие «по зову», и питомец не вызван |
| `not-open` | команда требует открытого вида (`room.*` вне редактора, предметы вне «Поиграть») |
| `treat-waiting` | сегодня ещё не было занятия |
| `treat-fed` | сегодня уже угостили |
| `already-started` | повторный `start()` |
| `destroyed` | экземпляр отключён |
| `internal` | внутренний сбой |

Отказ хранилища — не код ошибки команды: правка применена (`ok: true`), `save.status` — `'failed'` (или `'unavailable'` в снимке, если загрузка хранилища не удалась и запись запрещена, § 8.2).

### 6.5 Обязательное ядро и возможности отображения

Обязательны для ядра: хост-команды, настройки, `feed`, `interact({ type: 'pet' })`, присутствие, `hide`/`show`, снимок, подписка, жизненный цикл. Необязательны и объявляются отображением через `setDisplay({ views })`: виды `play` и `room`, перенос между местами (legacy), предметы «Поиграть». Неподдерживаемое — `unsupported`, без изменения состояния. Ядро не знает, что вид — это `HTMLDialogElement`, экран или модальное окно: `view.open` — только смысл.

### 6.6 Остаётся у хоста

Сохранение учебного действия и счёт знаков (`progress`); решение, что засчитывается; навигация и карточка следующего шага (legacy-настройки `step`, `go` — только отображению); тексты правил сайта; свои ошибки сохранения. Порядок хоста — сохранить действие → обновить счёт → `notify('saved', detail)`.

## 7. Расширения: питомец и модель поведения

### 7.1 Два независимых контракта

**`PetDefinition`** — кто это и как выглядит (данные):

| Поле | Что |
| --- | --- |
| `format: 1` | версия формата определения (не версия пакета и не версия данных `v1`) |
| `id` | уникальный ID: штатные — `cat`, `dog`; сторонние — с точкой (`example.bunny`), шаблон `^[a-z0-9-]+(\.[a-z0-9-]+)+$` |
| `title`, `forms` | подписи и формы слова («Кот», «кота») |
| `names` | имя по умолчанию, готовые варианты, предложение для знакомства |
| `coats` | облики `{ id, title }`, первый — по умолчанию |
| `accessories` | `{ id, title, stage }` — открываются ступенью |
| `items` | вещи по ступеням и их названия; подарки ступеней |
| `poses` | смысловые позы, которые рисуют наборы; `poseFallback` — замена недостающей позы |
| `micro`, `openMicro` | одиночные движения покоя и при открытии уголка |
| `actions` | действия и тексты итогов: `pet` («… мурлычет.»), `paw` (есть ли и текст) |
| `scenes` | варианты сценок `{ id, needs: 'any' \| 'full' }` |
| `size` | рамка рисунка (220×204) и земля — общие единицы для игры и комнаты |
| `play` | области попадания головы, тела, лапы (единицы рисунка) |
| `room` | рамки питомца на месте отдыха (`all`, `core`), рамка позы «ест», свои игрушки (клубок, канат, мячик) с исходными местами и рамками; общая мебель ступеней — из `pet/defs/room.mjs` |
| `fallback` | штатный питомец, которого показывают старые клиенты и отображения без набора (§ 7.5, § 7.7) |

**`BehaviorDefinition`** — как себя ведёт (данные):

| Поле | Что |
| --- | --- |
| `format: 1`, `id`, `title` | как у питомца; штатная модель — `calm` |
| `reactions` | таблица реакций: поза, длительность, приоритет, группа реплик, пауза повтора, признаки `decorative`, `calmOnly`, `toy`, `scene`, `still` |
| `timings` | интервалы моргания и движений по режиму, вероятность зевка, длительность реплики |
| `limits` | полных откликов поглаживания в минуту (≤ 3) |
| `scenes` | шанс (0 … 0,25) и порядок выбора вариантов |
| `phrases` | группы реплик: `default` (без признаков вида) и `byPet[petId]`; реплики кота и собаки 0.1.4 — в `byPet` штатной модели |

**Что модель изменить не может** (инварианты ядра, § 10): награда только после подтверждения; один знак — одна радость; праздник ступени не повторяется; одно лакомство за местный день; одна сценка за местный день в области хранения; одна попытка на событие; срок 10 с и задержка 500 мс; отложенная реакция одна и не дольше 60 с; тишина и «спрятан» — запрет, а не реакции; уменьшение движения; игра без знаков; лимит частоты не выше 0.1.4. Шанс сценки, лимиты и длительности модель может только уменьшать относительно этих границ.

### 7.2 Граница данных и кода

**Формат 1 — только данные.** Определения — сериализуемые объекты без функций; ядро исполняет их по своим правилам. Причины: одинаковое поведение на вебе и нативе, проверка до запуска, воспроизводимость, отсутствие произвольного кода в чужих определениях, простая сериализация для документации и тестов. Вторая модель поведения в PL06 строится данными (другие длительности, приоритеты в разрешённых пределах, реплики, варианты сценок, интервалы покоя).

**Исполняемые стратегии** (функции выбора реплики, сценки) в формате 1 не допускаются. Если они понадобятся, это новый формат определения отдельным решением: только доверенный локальный код, переданный импортом в приложении (никакой загрузки по сети, `eval`, `new Function`); чистые синхронные функции с контекстом из ядра (`random`, `now`, состояние только для чтения); результат проверяется; исключение — запасное решение формата 1 и `warning`.

Наборы отображения — код (компоненты, функции рисования), но они не принимают решений: получают позу, облик, предметы и рисуют.

### 7.3 Регистрация и проверка

- `definePet(def)` и `defineBehavior(def)` проверяют структуру и возвращают замороженное определение; ошибка — `PetError('definition-invalid', { path })`.
- Регистрация — **список на экземпляр**: `createPetCore({ pets, behaviors })`. Глобального изменяемого реестра нет: два экземпляра с разными наборами не мешают друг другу. Дубликат ID в списке — `duplicate-id`.
- `format`, которого ядро не знает, — `unsupported-format`. Совместимость с ядром — номер формата, не диапазон версий пакета.
- Проверки при создании (`incompatible-definitions`): каждая поза реакций модели есть у каждого питомца (или в `poseFallback`); группы реплик существуют, непусты, строки не длиннее 120 знаков; варианты сценок ссылаются на сценки питомца; числа в границах § 7.1; предметы и аксессуары имеют известные ступени.
- Наборы отображения регистрируются в отображении (`mountPetIn(el, { kits })`, `<PetView kits>`): набор покрывает все позы, облики и предметы своего определения (или объявленные замены); иначе отображение отказывает при создании. Набор без определения — ошибка отображения.

### 7.4 Ресурсы

Общий смысловой ID (поза `joy`, облик `ginger`, предмет `bowl`) связывает ядро и наборы. Веб-набор — SVG и CSS; нативный — компоненты `react-native-svg` и анимации. SVG-строка веба автоматически нативным ресурсом не считается; нативный набор рисуется заново по тем же единицам рисунка (220×204, сцена 400×250), чтобы геометрия ядра совпала с видом.

### 7.5 Отсутствующие и неизвестные ID

- **Сохранён ID, которого нет в этом экземпляре** (расширение не подключено, удалено, старое приложение): в снимке `pet.id` — сохранённый, `available: false`; `shown` — штатный питомец, записанный рядом с выбором (`ext:v1.pet.over`, § 7.7), а если его тоже нет — первый питомец списка `pets`. Выбор не перезаписывается, данные расширения (имя, облик, расстановка) не трогаются; когда определение снова подключат, питомец вернётся. Для модели — то же: показывается первая модель списка, `behavior.id` остаётся сохранённым.
- **Набор отображения недоступен** для зарегистрированного питомца: `setDisplay({ pets })` не содержит его → показывается `fallback`, сохранённое не меняется; `setPet` такого — `unsupported`.
- **Неподдерживаемое действие** (`paw` у питомца без лапы) — `unsupported`; поза, которой нет в наборе, — `poseFallback`, иначе базовая поза.

### 7.6 Владение настройками и общие лимиты

| Настройка | Чья | Где хранится |
| --- | --- | --- |
| имя, аксессуар | питомца | кот — `cat`, собака — `companion.dog`, расширения — `ext:v1.pets[id]` |
| облик | питомца | `look[petId]` |
| расстановка комнаты | питомца | `room[petId]` |
| движение, реплики, «скрыт», увиденная ступень, день приветствия | общая | `cat` |
| присутствие | общая | `presence` |
| выбранный питомец | общая | `companion.kind` (кот, собака); расширение — `ext:v1.pet` |
| модель поведения | общая | `ext:v1.behavior` |
| лакомство дня | общее для всех питомцев и моделей | `treat` |
| день сценки | общий для всех питомцев и моделей | область резервирования (§ 9) и копия `scene` |

Память обработанных событий и попыток сценки — на экземпляр ядра; смена питомца или модели её не сбрасывает (как `switchKind` 0.1.4).

### 7.7 Хранение данных расширений [цель, PL06]

Новые данные — в новом ключе, потому что вкладки 0.1.4 нормализуют `cat` и `companion` и отбросили бы их: `<ns>:ext:v1` = `{ v: 1, pet?: { id, over }, behavior?: string, pets?: { [id]: { name, accessory } } }`. Выбор расширения действителен, пока `companion.kind === over` (штатный питомец, который видят старые клиенты): если старая вкладка выбрала другого, побеждает её более поздний выбор. Выбор кота или собаки новым клиентом пишет `companion.kind` и убирает `ext:v1.pet`. Облик и расстановка расширения — новые поля верхнего уровня в `look` и `room`: их 0.1.4 сохраняет (README, «Хранение»).

### 7.8 Обновление и снятие расширения

Обновление определения с тем же ID и форматом — новая версия приложения; сохранённые настройки остаются (неизвестные значения — по правилам PL02: показ по умолчанию, запись не стирает). Снятие — следующий экземпляр создаётся без определения: § 7.5, данные сохраняются и вернутся при повторном подключении.

### 7.9 Кот и собака — штатные определения [цель, PL06]

Всё, что в 0.1.4 различается ветвлениями `kind === 'dog'` (`PROFILES`, `stageItems`, `stageGift`, `SCENES`, `NAME_PRESETS`, `DOG_PHRASES`, области `HIT`/`PAW`, рамки `PET`/`FEED` комнаты, мячик собаки), переходит в `pet/defs/cat.mjs` и `pet/defs/dog.mjs`; реплики — в модель `calm` (`byPet`). Проверка PL06: поведение и вид прежние (имеющиеся тесты и попиксельные снимки), в ядре нет ветвлений по виду.

### 7.10 Доказательство расширяемости (критерий PL06, ещё не выполнен)

Пример вне `pet/core` и `pet/defs` (например, `examples/extension/`) подключает третьего питомца `example.bunny` — простой рисунок, свои облики, без лапы, одна сценка `needs: 'any'` — и вторую модель `example.lively` (короче реакции, свои реплики, шанс сценки 0,15) только через публичные входы `pet-companion/core` и наборы отображения. Критерии: изменение примера не меняет файлов `pet/core/**`; в ядре нет новых ветвлений по ID; кот и собака работают как раньше; сохранённый `example.bunny` без подключённого определения показывает штатного питомца и не теряет данных; набор веба есть в PL06, нативный — в PL10. Большой набор графики, платные ресурсы и магазин не входят.

## 8. Хранение

### 8.1 Адаптер [цель, PL03]

Один адаптер на хранилище и пространство имён, общий для всех экземпляров ядра на нём; адаптеры возвращаются фабрикой из реестра модуля (`createWebStorage({ namespace })` — тот же объект для того же `namespace` в этой копии модуля; натив — для той же базы и `namespace`).

```ts
// Проект (PL03).
interface StorageAdapter {
  readonly status: 'idle' | 'loading' | 'ready' | 'failed';
  load(): 'ready' | 'failed' | Promise<'ready' | 'failed'>;  // веб — синхронно; натив — Promise
  read(key: string): string | null;                          // подтверждённое значение, синхронно
  write(key: string, build: (current: string | null) => string): boolean | Promise<boolean>;
  watch(listener: (key: string | null, oldText: string | null, newText: string | null) => void): () => void;
}
```

- `read` — последнее подтверждённое: веб — `localStorage.getItem` (своего кэша нет), натив — общий кэш адаптера.
- `watch` — подтверждённые изменения, сделанные **не этим экземпляром** (адаптер не сообщает автору его же операцию): веб — событие `storage` других вкладок и операции других экземпляров этой страницы на том же адаптере; натив — операции других экземпляров процесса. `key === null` — хранилище очищено целиком.
- Запись — только через `write`; прямых `setItem` вне адаптера нет.

### 8.2 Загрузка и готовность

`load()` первого экземпляра читает все ключи пространства имён в кэш; `load()` следующего (в том числе после `destroy` прежнего) завершается, когда разрешены все операции, уже стоящие в очередях адаптера, и отдаёт подтверждённое, а не принятое в очередь. Ядро создаётся только после загрузки: приветствие, первое включение, присутствие и место применяются к загруженному. `mountPet` не ждёт `load()`: веб-адаптер загружается синхронно в момент создания.

Четыре случая чтения ключа различаются [цель, PL02]:

| Случай | Показ | Запись |
| --- | --- | --- |
| ключа нет | умолчания | разрешена |
| значение повреждено (не JSON или не объект) | умолчания; `save[key].status` — `'saved'` (своих операций нет); при загрузке — эффект `warning` с кодом `corrupt` | неявные записи (приветствие дня, первое включение, отметка ступени при открытии) ключ **не трогают**; явная команда владельца заменяет повреждённое значение (понятых данных в нём нет — ограничение описывается) |
| отказ чтения (исключение хранилища) / отказ загрузки | умолчания в памяти | **никаких записей** (`status: 'failed'` адаптера, в снимке ключи — `'unavailable'`); подсказки — «не сохраняется»; новая попытка — при следующем подключении |
| более новая схема (`v` больше известного) | понятые поля | совместимая запись: неизвестные поля сохраняются, `v` не уменьшается. Несовместимый формат обязан использовать новый ключ (`:v2`), поэтому чужой `v` в том же ключе — совместимое дополнение |

### 8.3 Операция ключа и критический участок

В очередь ставится самодостаточная правка: `build(current)` — синхронная функция ядра с **захваченным при постановке** патчем (например, `(text) => JSON.stringify(catRecord(text, { name: 'Барсик' }))`). Она не читает живой экземпляр, ничего не ждёт и не меняется после `destroy`. Заранее собранный полный JSON в очередь не ставится.

Очередь — в адаптере, одна на хранилище, пространство имён и ключ, общая для экземпляров; операции ключа выполняются строго по порядку постановки, по одной; разные ключи независимы, транзакции между ключами нет и не обещается. Для операции в голове очереди:

1. `current` — подтверждённое значение, прочитанное внутри участка (кэш процесса; если ключ могут писать несколько процессов — само хранилище в его транзакции).
2. `next = build(current)` — сразу после шага 1. Исключение в `build` — отказ (`false`), ничего не записано. `next === current` — `true` без записи и без уведомлений.
3. Запись `next` целиком и атомарно, ожидание подтверждения.
4. Подтверждено: кэш = `next`; затем `watch` каждому другому экземпляру; затем результат автору — `true`. Отказ: кэш прежний, уведомлений нет, автору — `false`.
5. Следующая операция ключа начинается только после шага 4; реакция автора на результат выполняется раньше неё (асинхронный адаптер начинает следующую не раньше следующей задачи после разрешения обещания).

Успех предыдущей операции меняет основу следующей; отказ оставляет прежнюю основу.

### 8.4 Состояние ключа в экземпляре

- **подтверждённое** — `read(key)`;
- **свои операции** — номер `n` (растёт с каждой правкой ключа в экземпляре) и патч; без результата — неразрешённые;
- **несохранённые поля** — поля операций, получивших `false`, ещё не отправленные снова;
- **в памяти** — подтверждённое, поверх него несохранённые поля, поверх — патчи неразрешённых по возрастанию `n`, той же функцией записи ключа, что в `build`: память совпадает с тем, что будет записано;
- **статус** — `pending`, если есть неразрешённые; иначе `failed`, если есть несохранённые поля; иначе `saved`; при отказе загрузки — `unavailable`.

Правка ключа: изменённые поля — в памяти сразу; новая операция `n` с патчем «несохранённые поля ключа + поля правки» (несохранённые переходят в неё: следующая правка снова пишет всё несохранённое, как 0.1.4). Повторов и таймеров нет.

Результат операции `n` — одна обработка `settle(n, ok)`: `true` — операция разрешена, её значение уже в `read`; если остались неразрешённые `n + 1…` — статус остаётся `pending` (подтверждение старой правки не означает сохранения новой). `false` — поля её патча, не перекрытые более поздними неразрешёнными операциями экземпляра, становятся несохранёнными: действуют в памяти до перезапуска, правка не откатывается.

### 8.5 Синхронный веб и асинхронный натив

```js
// Проект обработки результата (PL03).
const result = storage.write(key, build);
if (typeof result === 'boolean') settle(n, result); // в этом же вызове
else result.then((ok) => settle(n, ok === true), () => settle(n, false));
```

- `boolean` — **окончательный** результат уже при возврате: `true` — записано и подтверждено; `false` — отказ. Асинхронный адаптер синхронно может вернуть только `false` (операция не принята: хранилище недоступно); синхронного `true` поверх кэша у него нет.
- `Promise<boolean>` — операция принята в очередь; это **не** «сохранено». Обещание обязано завершиться: `true` — хранилище подтвердило; `false` или отклонение — отказ.
- **Веб** остаётся синхронным: `getItem` → `build` → `setItem` → `settle` → снимок и объявление в том же вызове, без микрозадач между записью и объявлением. `Promise.resolve(syncResult).then(…)` нарушил бы порядок 0.1.4 (отрисовка и объявление ушли бы со статусом `pending`), поэтому запрещён. Видимого `pending` в вебе нет.
- **Натив:** в том же вызове — `pending`, правка в памяти, реакция идёт; объявления без «сохранено» и без «не сохранилось» (отображение может показать «Сохраняется…»). По результату — `saved` и, где 0.1.4 сообщает о сохранении, это сообщение; `failed` — подсказки и отдельное позднее объявление. Поздняя ошибка не теряется.
- После `destroy` `settle` экземпляра ничего не делает.

### 8.6 Внешние изменения

`watch(key, old, new)`: кэш уже обновлён; ядро пересчитывает память ключа: несохранённые поля, которые эта запись изменила, забываются (подтверждённая там правка новее неудавшейся здесь, как 0.1.4); поле, подтверждённое значение которого совпало с памятью, — тоже; патчи своих неразрешённых операций не трогаются — они стоят в очереди позади этой записи и лягут поверх неё. Затем — одно обновление подписчикам.

### 8.7 Сценарии

Ключ `cat`, подтверждено `{ name: 'Марс', motion: 'normal' }`, экземпляры A и B на одном адаптере.

**Независимые поля (асинхронный адаптер).**

| Шаг | Очередь `cat` | Подтверждено | Память A | Память B |
| --- | --- | --- | --- | --- |
| 1. A: `setName('Барсик')` → A1 `{ name }` | A1 | Марс, normal | Барсик, normal (`pending`) | Марс, normal |
| 2. B: `setPreferences({ motion: 'none' })` → B1 `{ motion }` | A1, B1 | Марс, normal | Барсик, normal | Марс, none (`pending`) |
| 3. A1: `current` = Марс, normal → Барсик, normal; подтверждено; B получает `watch` | B1 | Барсик, normal | Барсик, normal (`saved`) | Барсик, none (`pending`) |
| 4. B1 начинается только теперь: `current` = Барсик, normal → Барсик, none | — | Барсик, none | Барсик, none (после `watch`) | Барсик, none (`saved`) |

Итог — обе правки. Если бы B собрал полный JSON `{ Марс, none }` на шаге 2, запись A → B вернула бы имя «Марс» — поэтому так нельзя. Веб даёт тот же итог синхронно: каждая правка — свой вызов `getItem → build → setItem`.

**Конфликт одного поля:** A ставит `Барсик`, затем B — `Пиксель`. Побеждает поставленная позже: после A1 у A — Барсик (`saved`), у B — Пиксель (`pending`); после B1 у всех — Пиксель. Отказ B1: подтверждено и у A — Барсик; у B — Пиксель несохранённым (`failed`, «не сохранилось»); следующая подтверждённая внешняя правка имени это поле у B заменит.

**Разные животные в одном ключе:** A меняет облик кота в `look`, B — облик собаки: патчи `{ cat }` и `{ dog }` не пересекаются, сохраняются оба. Имя кота (`cat`) и имя собаки (`companion.dog`) — разные ключи, независимы.

**Отказ, затем правка:** A1 `{ name }` — отказ → `name` несохранённым (`failed`). A2 `{ motion }` → патч `{ name, motion }`; успех — оба сохранены, `saved`.

**Внешняя правка перед своей операцией:** B поставил B1 `{ motion: 'none' }`; до неё подтвердилась A1 `{ motion: 'calm' }`. B получает `watch`, память B — `calm` + патч B1 → `none` (`pending`); после B1 у всех — `none`. Порядок очереди решает.

**Нет изменения и исключение `build`:** `next === current` — `true` без записи и уведомлений, статус `saved`. Исключение — `false`, поля патча несохранённые, `warning`.

**Отклонение обещания** — как `false`; необработанных отклонений нет (обработчики подключаются в вызове команды).

**Два экземпляра, разные `namespace`:** разные адаптеры и очереди, данные независимы. **Повторное подключение:** новый `load()` ждёт операций, поставленных прежним экземпляром, и видит подтверждённое; несохранённые правки прежнего не наследуются.

**Завершение процесса до подтверждения:** неподтверждённая правка может потеряться; ядро не считало её сохранённой; после перезапуска `load()` покажет то, что действительно записано. Лакомство того же дня после такого сбоя может снова стать доступным.

### 8.8 `destroy` и очередь

- новые команды экземпляра не выполняются; экземпляр снимается с `watch`; несохранённые правки теряются (как перезагрузка 0.1.4);
- операция, уже принятая адаптером, **не отменяется**: `build` самодостаточен, поэтому правка, сделанная до `destroy`, ляжет на актуальное подтверждённое и не затрёт поля других экземпляров; подтверждение обновит кэш и придёт живым экземплярам через `watch`; результат прежнему экземпляру — без действий;
- освобождение очереди зависит только от результата операции, не от жизни автора;
- новый экземпляр видит такие операции только подтверждёнными (его `load()` ждёт очереди).

### 8.9 Пределы гарантий

| Область | Гарантия | Чего нет |
| --- | --- | --- |
| один процесс / одна страница, один адаптер | порядок операций ключа, независимые правки разных полей не теряются, честный статус | транзакций между ключами |
| вкладки одного браузера (`localStorage`) | синхронная запись по свежему значению, `storage` в других вкладках | межвкладочной транзакции read-modify-write: окно 0.1.4 (Р4) остаётся; очередь JS его не устраняет |
| несколько процессов с общей базой (натив) | только если шаги 1–3 идут в транзакции хранилища (SQLite) | уведомлений между процессами без поддержки хранилища; общий кэш и очередь процесса другой процесс не защищают |
| устройства, браузеры, приложение и сайт | — | синхронизации: у каждого хранилища свои настройки и лимиты |

### 8.10 Адаптеры

- **Веб** (`createWebStorage`, PL03): `localStorage`; адаптер создаётся уже загруженным — `load()` синхронно возвращает тот же итог (`'failed'`, если доступ к `localStorage` бросает исключение); `write` синхронно возвращает `boolean`; `watch` — событие `storage` и операции других экземпляров этой страницы на том же адаптере. Разные копии модуля на одной странице не делят реестр адаптеров — для общего `namespace` держите одну копию (в legacy один питомец на странице).
- **Натив** (`createSqliteStorage`, PL09): SQLite через `expo-sqlite`. Таблица `(ns, key, value)`; запись — `withExclusiveTransactionAsync`: чтение `current`, `build`, `INSERT OR REPLACE` в одной исключительной транзакции. **Подтверждение** — разрешённое обещание этой транзакции (COMMIT выполнен). Запись в кэш, отложенная запись без результата (как `SharedPreferences.apply()`) подтверждением не считаются. После подтверждения данные переживают завершение процесса; устойчивость к отключению питания зависит от режима журнала и `synchronous` SQLite — режим выбирается и описывается в PL09, большего не обещается. Конфликт блокировки с другим процессом (`SQLITE_BUSY` после ожидания) — отказ операции, без скрытых повторов.

## 9. Атомарное резервирование сценки

### 9.1 Интерфейс [цель, PL04]

```ts
// Проект (PL04).
interface SceneReserver {
  reserve(decide: (stored: object | null) => object | null, show: () => void): Promise<'shown' | 'skip' | 'fail' | 'lost'>;
}
```

`decide` и `show` — синхронные функции ядра. `sceneTurn` и IndexedDB — веб-адаптер (`createWebScenes`), а не зависимость ядра. Обычные независимые `get`/`set` резервирование не заменяют.

| Результат | Смысл |
| --- | --- |
| `shown` | показ начался, день записан и подтверждён; прерванный потом показ день не освобождает |
| `skip` | решили не показывать (отменено, не подходит, день занят) — ничего не записано и не показано |
| `fail` | нет хранилища или блокировки, чтение или запись не начались, сбой до показа — ничего не показано, день свободен, повтора нет |
| `lost` | показ начался, запись не подтвердилась — останавливается только этот показ, если он ещё текущая реакция экземпляра; день свободен; частичной записи нет |

### 9.2 Порядок

1. Войти в общую блокировку хранилища и пространства имён (одна на адаптер, не на экземпляр; ожидание может длиться).
2. Прочитать актуальную подтверждённую запись дня **внутри** защищённого участка. Отказ — `fail`.
3. `decide(stored)` перепроверяет: экземпляр жив; попытка та же и не отменена; срок ≤ 10 с от подтверждения занятия; нет тишины; приложение и питомец видны (присутствие, «спрятан», «по зову»); ничего не играет; закрыты «Поиграть» и редактор; нет переноса; вариант читается в текущем показе (целиком/портрет) и есть в наборе отображения; день занятия — сегодня (полночь — без сценки); день не занят в записи и в копии `scene`. Не подходит — `null` → `skip`.
4. Поставить запись дня и **сразу** вызвать `show()` в том же синхронном шаге, что и решение: показ начинается после постановки записи и до её подтверждения, между проверкой и началом показа состояние не меняется. Порядок «сначала дождаться записи, потом показать» не допускается: проверенные условия успели бы устареть.
5. Держать блокировку до подтверждения или отказа записи.
6. Результат применить только к актуальному экземпляру и только к этой попытке. При `shown` и живом экземпляре ядро пишет копию дня `scene` обычной операцией хранилища (§ 8) — в пространство имён, захваченное при старте попытки.

`decide` бросил исключение — отмена до показа, `fail`. `show` бросил после постановки записи — отмена транзакции, `lost` (как 0.1.4).

### 9.3 Отмена, `destroy`, повторное подключение

- Отмена до резервирования (тишина, ввод, ручное действие, смена питомца, облика, места, движения, «Поиграть», перенос, фон) снимает попытку; если `reserve` уже в очереди, `decide` увидит другую попытку → `skip`. Адаптер может снять операцию и раньше — тоже `skip`.
- `destroy` до `decide` → `skip`, ничего не записано.
- `destroy` после начала показа, до результата: запись не отменяется, день может подтвердиться и остаётся. Поздний результат прежнему экземпляру ничего не делает: ни копии дня, ни остановки, ни воздействия на новый экземпляр (с любым пространством имён).
- Блокировка принадлежит адаптеру и освобождается по результату записи независимо от `destroy`.
- Новый экземпляр на том же хранилище и пространстве имён читает запись под той же блокировкой: день, занятый прежним, — второй сценки в этот день нет.

### 9.4 Механизм по адаптерам

| Шаг | Веб (IndexedDB `<ns>:scene`, PL04 из `sceneTurn`) | Натив (SQLite, PL09) |
| --- | --- | --- |
| 1 | readwrite-транзакция хранилища `scene`: браузер выполняет такие транзакции по очереди для всех вкладок и экземпляров источника | очередь (мьютекс) процесса на базу и пространство имён + `withExclusiveTransactionAsync` (исключительная транзакция SQLite) |
| 2 | `get('shown')` в этой транзакции | `SELECT` записи сценки в этой транзакции |
| 3 | `decide` в `get.onsuccess` | `decide` в том же продолжении, где получен результат `SELECT` |
| 4 | `put(record, 'shown')`, затем сразу `show()` | вызов `INSERT OR REPLACE` (обещание ещё не ждём), затем сразу `show()` |
| 5 | транзакция активна до `oncomplete`/`onabort` | транзакция до COMMIT/ROLLBACK |
| 6 | `oncomplete` → `shown`; `onabort` → `lost` или `fail` | COMMIT → `shown`; ошибка → ROLLBACK, `lost` или `fail` |
| Граница | вкладки одного источника в одном профиле браузера | один процесс — очередью; несколько процессов с общим файлом — исключительной транзакцией SQLite; занятая база — `fail` |
| Нет механизма | IndexedDB недоступна — сценки нет | адаптер не передан — сценки нет |

Копия `scene:v1` в `localStorage` нужна вебу для вкладок старых версий (они проверяют и её): запись дня и копия согласуются, как в 0.1.4. Разные хранилища (Safari и приложение с экрана «Домой», браузер и приложение, два устройства) — независимые лимиты.

## 11. Веб

### 11.1 Legacy-режим

`mountPet` с местами `logo`, `top`, `sidebar`, `float`, `bar`, `restore`, реестром одного питомца на странице, id `cat-*`, отметками на `<html>` и блокировкой прокрутки сохраняется без изменения поведения. С PL03 это фасад: ядро + веб-адаптеры + legacy-отображение (`pet/web/legacy/**`, бывшая DOM-часть `pet.mjs`, места `pet-place.mjs` и перенос `pet-move.mjs`). Ключ `place:v1` — предпочтение legacy-отображения: его формат и правила раскладки (`petLayout`, `PLACE_MEDIA`) остаются в веб-слое, запись — через тот же адаптер хранения (§ 8, с PL04). Распознавание ввода в текстовые поля страницы (`focusin`/`focusout`, 250 мс) — legacy-отображение, в ядро — `setContext({ typing })`.

### 11.2 Контейнерный режим [цель, PL07]

- `mountPetIn(container, options) → PetView`: синхронно, не бросает (отказ — `view.mounted === false`, `console.error`), `view.core`, `view.open(view)`, `view.close()`, `view.destroy()`. Создаёт свой элемент внутри контейнера и **открытый Shadow DOM** на нём. Почему Shadow DOM: изоляция id, классов и стилей в обе стороны без префиксов и без требований к стилям хоста; переменные темы `--pet-*` наследуются через границу — хост по-прежнему меняет тему. Равноценный способ (префиксы и сброс стилей) отклонён: не защищает от правил хоста с классами и `!important`.
- Размеры — по контейнеру (`ResizeObserver` и контейнерные запросы), а не по окну; мест страницы нет: одно место — контейнер, вид «целиком» или «портрет» по его размеру.
- Хост не меняется: никаких отметок на `<html>`, блокировки прокрутки и глобальных стилей. Открытые виды — `<dialog>` внутри теневого дерева (`showModal`, ловушка фокуса, Esc — шаг назад, как 0.1.4); блокировку прокрутки решает хост через `onOpenChange(open)`.
- Фокус: при закрытии — на кнопку, открывшую вид; иначе `options.home()`. Объявления — своя область `aria-live` в теневом дереве и в открытом диалоге.
- Ввод хоста: слушатель `focusin`/`focusout` документа (только чтение) → `setContext({ typing })`; опция `watchTyping: false` отключает.
- Два контейнера — два экземпляра ядра и отображения, ни один не отключает другой; общий `namespace` — общий адаптер хранения и общий дневной лимит, разный — независимы. Изоляция DOM и совместность хранения — независимые настройки.
- Состояние отображения (жесты, перенос, игрушки) — на экземпляр отображения, не на модуль (Р3).
- Legacy-реестр одного питомца контейнерный режим не использует.

### 11.3 React и SSR [цель, PL08]

`<PetCompanion namespace progress … />` подключает контейнерный режим в `useEffect` и отключает при размонтировании; в StrictMode последовательность «подключить → отключить → подключить» корректна (повторный `destroy` безопасен, новый экземпляр видит подтверждённое). `usePetState(core)` — `useSyncExternalStore(core.subscribe, core.getState)`. Импорт `pet-companion/core`, `/pets`, `/behaviors`, `/react` на сервере не обращается к браузерным глобалам; подключение — только в эффекте.

### 11.4 Файлы пакета [цель, PL08]

`exports` перечисляет входы § 6.1; `sideEffects` — только CSS legacy. Для серверов без сборщика — `manifest.json`: версия и для каждого входа список файлов, которые нужно отдавать, и порядок стилей; потребитель больше не держит ручной список внутренних модулей. Проверка: перечень совпадает с содержимым архива; потребитель в чистой папке отдаёт файлы по перечню.

### 11.5 CSP

Строгий CSP **не поддерживается** в 0.1.4: разметка вставляется через `innerHTML` с атрибутами `style`, без `'unsafe-inline'` в `style-src` вид может нарушиться (README). Цель (PL07, заявление поддержки — PL13 после проверки): без атрибутов `style` в разметке (динамические значения — `element.style.setProperty`), без встроенных `<style>` и скриптов; стили — файлом пакета (`<link>` в теневом дереве) или `adoptedStyleSheets`; итоговый механизм выбирается в PL07 по проверке под `default-src 'self'; style-src 'self'` в Chrome, Safari и Firefox. CSP существующих потребителей не ослаблять ради питомца.

### 12.2 Нативное отображение [цель, PL10]

- Компоненты `PetView` (питомец на экране хоста), `PetCorner`, `PetPlay`, `PetRoom` получают ядро и наборы; рисуют снимок, превращают касания в команды (`interact`, `room.move`, `open`, `close`), не дублируют правил (лимиты, сценки, лакомство — в ядре).
- Рисунки — `react-native-svg` по тем же единицам (220×204, сцена 400×250); анимации — встроенный `Animated` (дополнительные библиотеки анимаций и жестов — только если PL10 обоснует); позы и движения — по смысловым ID набора.
- Жесты: распознавание поглаживания, касания лапы, переноса предмета — в отображении (пороги в точках экрана); смысл — команда ядра.
- Доступность: подписи и роли, объявления эффекта `announce`, системное уменьшение движения → `setReducedMotion`. Безопасные области — отступы от хоста (свойство `insets`), без обязательной зависимости. Поворот — размеры по `onLayout`.
- Жизненный цикл (`useNativeLifecycle(core)`): `AppState` `active` → `setVisible(true)`, `background` → `setVisible(false)`; `inactive` (iOS: центр уведомлений, переключатель приложений, звонок) видимость не меняет, но отменяет идущий жест — как наложение поверх страницы в вебе. Android «Назад» — шаг назад, как Esc: «Поиграть»/редактор → уголок → закрыть.
- Контекст занятости (ввод, таймер) нативный хост передаёт `setContext` сам; помощник по событиям клавиатуры — эвристика, необязательный.

### 12.3 Хранение и резервирование натива [цель, PL09]

SQLite через `expo-sqlite` (§ 8.10, § 9.4). Почему не `AsyncStorage`/`Preferences`: нет транзакций для резервирования сценки между процессами, подтверждение записи у разных реализаций различается; адаптеры по тому же контракту допустимы, но с объявленной границей «один процесс». `expo-sqlite` в «голом» React Native требует модулей Expo — условие подключения описывается.

## 14. Этапы реализации

### 14.1 Срез PL03

Минимальный законченный срез, которым пользуется веб:

- `pet/core/**`: `createPetCore`, `start`, `destroy`, порты `clock`, `random`, `scheduler`, `log`; результат и коды ошибок; снимок и подписка для полей среза.
- Координатор хранения (§ 8) с синхронным и асинхронным результатом; веб-адаптер `localStorage`; тестовый асинхронный адаптер с ручным подтверждением (только в тестах).
- Ключи `cat`, `companion`, `look`, `treat` переходят в ядро целиком: каждый их писатель в оболочке заменён командой ядра — имя, выбор кота или собаки, облик, аксессуар, движение, реплики, «скрыт», увиденная ступень, день приветствия, день лакомства.
- Счёт и ступени (`refresh`, первое включение, `seenStage`), решение подтверждённого действия (`notify('saved'|'failed')`: радость/поддержка, праздник, вещи, подсказка про миску, запись `seenStage`), решение и запись лакомства (`feed`), решение и запись приветствия.
- Веб: `pet.mjs` вызывает ядро для всего перечисленного; функции `readCat`, `readCompanion`, `readSettings`, `store` (для этих ключей), `updateSettings`, `forgetOverwritten`, `readLook`, `storeLook`, `forgetLook`, `fedDay`, `storeTreat`, расчёт ступени и лакомства в `refreshInfo`, решающие части `saved`, `failed`, `feed` и приветствия **удаляются** из оболочки. Синхронный порядок 0.1.4 и `mountPet` без ожидания сохраняются.
- Входа `pet-companion/core` в `exports` нет до PL05: ядро внутреннее, его поверхность ещё меняется.
- Проверки: Node с браузерными глобалами-ловушками; управляемые время, случайность и планировщик; два экземпляра на одном адаптере (сценарий «Марс → Барсик» § 8.7 и остальные сценарии § 8.7 для четырёх ключей); синхронный успех и отказ в том же вызове; асинхронный успех, отказ, отклонение; отказ загрузки без записей; `destroy` с операцией в очереди и повторное подключение; прежние `npm test`, `npm run test:browser`, `npm run test:package` — зелёные (число проверок может вырасти). В отчёте — явный список оставшегося до PL04; частичное ядро не называется законченным.

**Остаётся до PL04:** режиссёр и проигрывание реакций, их задачи и продолжения; тишина, активность, контекст страницы; покой, моргание, движения, зевок, полночь; видимость; выбор реплик и облака; сценки и резервирование; присутствие, «по зову», оркестровка «Скрыть»/«Показать»; открытые виды и их источник; комната (геометрия без импорта рисунка, черновик, сохранение, сдвиг к миске); игра (взаимодействия, лимиты, позиции игрушек); ключи `presence`, `room`, `scene`, запись `place` через адаптер; исправление Р1.

### 14.2 Предлагаемое разбиение больших этапов

PL04 и PL10 велики для одного законченного среза; разбиение внесено в очередь разработки как подзадачи с сохранением родительского ID и общих критериев:

- **PL04.1** реакции и время (режиссёр, проигрывание, тишина, контекст, покой, полночь, видимость, реплики, приветствие — проигрывание, Р1); **PL04.2** присутствие, виды и сценки (присутствие, скрыть/показать/позвать, `open`/`close`, праздник по виду, выбор сценки, порт резервирования, веб-адаптер IndexedDB, копия дня); **PL04.3** комната и игра (геометрия, редактор, сохранение, сдвиг к миске, `interact`, игрушки, лимиты, граница жестов). PL04 готов, когда выполнены все три и вся таблица § 13.
- **PL10.1** минимальный нативный потребитель на iOS и Android (питомец, имя, облик, подтверждённое действие и реакция, кормление, перезапуск, фон и возврат, уменьшение движения, отключение); **PL10.2** «Поиграть», «Обустроить уголок», расширения PL06 на нативе, поворот и безопасные области, доступность. ## 15. Совместимость и версии

- **Версии раздельны:** пакет (semver, `package.json` = `VERSION`); форматы данных (`v1` в ключах); формат определения (`format: 1`); формат снимка (`v: 1`).
- **До 1.0** — по README и CONTRIBUTING: совместимые исправления и дополнения — patch; несовместимое изменение публичного интерфейса — minor с описанием в CHANGELOG. Номер выбирается при выпуске; будущие номера здесь не обещаются.
- **Данные:** новые клиенты читают старые форматы или имеют проверяемый переход; неизвестные поля, ID и значения сохраняются по контракту PL02; повреждение и более новая схема не разрешают разрушительную запись (§ 8.2); миграции на личных данных при проектировании и в тестах не запускаются.
- **Старые вкладки:** открытая вкладка 0.1.4 выполняет свой код и может отбрасывать новые поля в `cat` и `companion`; исправление новой версии её не «лечит». Поэтому новые данные — в новых ключах (`ext:v1`, § 7.7) или там, где 0.1.4 их сохраняет.
- **Выпуски:** этапы PL02–PL10 завершаются проверенным локальным коммитом и зелёными проверками; выпуск в npm на промежуточном этапе — по решению владельца (публикация требует подтверждения владельца). PL11 требует опубликованной версии. Статусы различаются: реализовано, закоммичено, выпущен архив, опубликовано в npm, подключено потребителем, опубликовано в облаке потребителя, проверено на устройстве.
- **1.0** — только после выполнения обязательных критериев, стабилизации API, схем и формата определений и подтверждения заявленных платформ на устройствах (PL13).
- Выпуск библиотеки не обновляет установленное мобильное приложение: потребитель собирает и доставляет его сам.

## 16. Коммерческие границы

Лицензия MIT не меняется. Возможные предложения (PL13): поддержка и интеграция, отдельные наборы питомцев и ресурсов, дополнительные адаптеры. Права и происхождение рисунков и зависимостей, уведомления лицензий, руководство автора питомца — PL13. Не входят и автоматически не разрешены: платежи, магазин, цены, закрытие публичного кода, клиентский сервер, лицензирование сверх MIT, универсальный SDK для всех платформ.

## 17. Решения владельца, которые понадобятся позже

- PL09–PL10: установка зависимостей примера, доступ к iPhone и Android-устройству или разрешение на симулятор, эмулятор и toolchain (§ 12.4).
- Выпуски в npm (подтверждение владельца при публикации); промежуточные выпуски до PL11 — по желанию.
- Если появятся расходы (облачные сборки, платная учётная запись разработчика), изменения доступа, секретов или лицензии — только отдельным решением.

## 18. Отличия от предыдущего предложения ядра

До этого проекта ядро предлагалось только для нативного сценария и откладывалось. Теперь оно — цель серии и для веба. Уточнено: загрузка адаптера — синхронная (веб) или асинхронная (натив) с одним контрактом; ядро сохраняет неизвестные поля по PL02, а не прежнюю потерю; создание и запуск разделены, чтобы отображение подписалось до первых эффектов; подписка получает начальный снимок синхронно; регистрация расширений — список на экземпляр; мобильная семья — React Native, хранение — SQLite. Контракты очереди записи (`write(key, build)`) и резервирования сценки сохранены без изменения смысла.
